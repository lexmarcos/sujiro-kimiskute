## Dependency notes

- **Everything depends on 001** because `cargo clippy -- -D warnings` fails at
  `HEAD` (`src/discord/handler.rs:67`). Until that is fixed, an executor cannot
  distinguish its own lint failures from the pre-existing one, and every other
  plan uses clippy as its verification gate.
- **004 depends on 002** because both reduce the cost of the observer fan-out
  and 004's premise is that the fan-out is fast once the panel returns promptly.
  002 makes the presence observer cheap; landing 004 first would leave the
  presence gateway spam in place and make 004's manual timing checks noisy.
  They touch disjoint files (`presence.rs` + `guild_player.rs` vs
  `player_panel.rs`), so there is no merge conflict — only an ordering
  preference.
- **003 is independent** of 002 and 004 and may be done at any point after 001.
- 001 and 002 both touch `src/discord/handler.rs`/its call sites conceptually,
  but 002 is explicitly written to keep `PresenceService::initialize`
  synchronous so it does **not** edit `handler.rs`. If an executor finds itself
  editing `handler.rs` during 002, that is a STOP condition.

## Findings considered and rejected

- **`ytsearch1:{query}` argument injection**: not a vulnerability. The user
  query is always prefixed with `ytsearch1:` and passed through
  `tokio::process::Command::args` (`src/sources/youtube/process.rs:61-68`), never
  a shell, so it can never be parsed as a `yt-dlp` flag. URL inputs are
  additionally host-allowlisted to YouTube (`src/sources/youtube/resolver.rs:207-235`).
- **Committed secrets**: none. `.env` is gitignored and `git log --all --diff-filter=A`
  confirms only `.env.example` was ever committed. The Discord token is never logged.
- **`install.sh` supply chain**: verifies a SHA256 checksum for both the release
  archive and the `yt-dlp` binary before installing. No finding.
- **Test coverage**: `AGENTS.md` explicitly forbids tests in this phase, so
  "add a test suite" is out of bounds by project decision, not oversight. The
  verification baseline is instead the fmt/clippy/build gate — plan 001.
- **`GuildPlayer::record_completed_track` uses `==` rather than `>=`**
  (`src/player/guild_player.rs:388`): safe, because history only ever grows one
  element at a time through that single call site. Fragile but not a bug; not
  worth a change.
- **`TrackQueue::restore_current_to_front` can exceed `max_size`**
  (`src/player/queue.rs:50-53`): deliberate and documented in a comment; the
  overflow is bounded by history length, which is itself bounded by `max_size`.
- **Deadlock between `GuildPlayerState` and `PlayRequestSequencer` locks**:
  investigated and rejected. Lock acquisition is consistently state → sequencer
  (e.g. `src/player/guild_player/play_requests.rs:19-24`); the sequencer never
  acquires the player state lock, so no cycle exists.

## Known findings not yet planned

Reported in the audit, not selected for planning in this round:

- **~8 unused `pub` methods** (`PlaybackService::play_single`/`enqueue`,
  `GuildPlayer::enqueue`/`enqueue_prefix`/`pop_next`/`queue_snapshot`/`clear_queue`,
  `PlayerManager::remove`). Invisible to the `dead_code` lint because they are
  `pub` in a binary crate. S effort, LOW risk. Decide alongside the queue
  management direction item below — the queue methods are either the skeleton of
  unbuilt `/remove` and `/clear` commands, or deletable.
- **Single-shard presence assumption**: `PresenceService` stores one
  `ShardMessenger` in a `OnceCell` set from `ready`
  (`src/discord/handler.rs:57`). Latent only — the bot runs one shard today via
  `client.start()`. Documented in plan 002's maintenance notes.
- **Direction items** (options, not defects): a missing `/previous` slash
  command despite the panel button and `PlaybackService::previous` both
  existing; unbuilt queue-management commands implied by the dead code above; a
  `CompositeResolver` spike to validate that `TrackResolver` really admits
  Spotify without touching command handlers, as `AGENTS.md` requires.
